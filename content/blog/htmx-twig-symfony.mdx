Une interface qui se met à jour sans recharger la page ne demande pas forcément une application monopage. [HTMX](https://htmx.org/docs/) permet de déclarer, directement dans le HTML, qu'un clic ou une saisie doit appeler le serveur et remplacer une partie de la page par le fragment reçu. Avec Twig, qui produit déjà le HTML, l'équipe garde un seul langage de gabarit et aucun JavaScript applicatif à maintenir. Cet article construit une recherche en direct, une pagination et un formulaire validé côté serveur, sur Symfony 8.1.9 avec HTMX 2.0.11, puis les teste.

## Le principe de HTMX

HTMX étend le HTML avec des attributs `hx-*`. Quelques-uns suffisent pour la majorité des cas :

- `hx-get`, `hx-post` : la requête à envoyer, sur n'importe quel élément.
- `hx-trigger` : l'événement déclencheur, comme `input changed delay:300ms` pour une saisie temporisée.
- `hx-target` : l'élément à remplacer, désigné par un sélecteur CSS.
- `hx-swap` : la manière de remplacer, par exemple `outerHTML` pour substituer l'élément lui-même.
- `hx-push-url` : écrit l'adresse dans l'historique du navigateur.
- `hx-boost` : transforme les liens et formulaires classiques en requêtes asynchrones, sans autre attribut.

Le serveur ne renvoie pas du JSON mais du HTML. C'est un changement de modèle par rapport à une [API REST](/article/api-rest-les-bonnes-pratiques) consommée par un client JavaScript : ici, la présentation reste côté serveur, et les règles métier ne sont écrites qu'une fois.

## Installer HTMX dans Symfony

Sans Node, [AssetMapper](https://symfony.com/doc/current/frontend/asset_mapper.html) suffit :

```bash
php bin/console importmap:require htmx.org
```

La commande a installé la version 2.0.11. Il reste à l'importer dans `assets/app.js` avec `import 'htmx.org';`. Aucune autre configuration n'est nécessaire.

## Détecter les requêtes HTMX et renvoyer des fragments

HTMX ajoute l'en-tête `HX-Request: true` à chacune de ses requêtes. Le contrôleur s'en sert pour choisir entre la page complète et le fragment :

```php
#[Route('/articles', name: 'articles')]
public function index(Request $request, ArticleRepository $articles): Response
{
    $query = trim((string) $request->query->get('q', ''));
    $result = $articles->search($query, $request->query->getInt('page', 1), 5);

    $isFragment = 'true' === $request->headers->get('HX-Request')
        && !$request->headers->has('HX-Boosted')
        && !$request->headers->has('HX-History-Restore-Request');
    $response = $this->render($isFragment ? 'article/_results.html.twig' : 'article/index.html.twig', [
        'query' => $query,
        'result' => $result,
    ]);
    $response->headers->set('Vary', 'HX-Request, HX-Boosted, HX-History-Restore-Request');

    return $response;
}
```

Trois détails comptent. D'abord, une navigation `hx-boost` envoie aussi `HX-Request`, mais attend une page entière : l'en-tête `HX-Boosted` permet de la distinguer. Il en va de même, d'après la documentation de HTMX, de la restauration de l'historique du navigateur quand l'instantané n'est plus en cache, signalée par `HX-History-Restore-Request`. Nous n'avons pas réussi à provoquer ce cas dans Chromium, mais la condition est inoffensive et le test serveur la couvre. Ensuite, comme une même URL renvoie un fragment ou une page selon ces trois en-têtes, la réponse doit déclarer `Vary` sur chacun d'eux, sans quoi un cache HTTP pourrait servir un fragment à une navigation complète. Enfin, le gabarit de page inclut le même fragment que celui renvoyé aux requêtes HTMX : une seule source de vérité.

## Recherche en direct et pagination

Le champ de recherche déclare son comportement dans le HTML :

```twig
<form action="{{ path('articles') }}" method="get" role="search">
    <label for="q">Rechercher</label>
    <input id="q" type="search" name="q" value="{{ query }}"
           hx-get="{{ path('articles') }}"
           hx-trigger="input changed delay:300ms, search"
           hx-target="#results"
           hx-replace-url="true">
    <button type="submit">Rechercher</button>
</form>
```

La saisie est temporisée de 300 millisecondes, le résultat remplace le contenu de `#results`, et l'adresse est mise à jour avec `hx-replace-url`, qui évite d'ajouter une entrée d'historique à chaque pause de frappe. Dans le navigateur, avec Chromium piloté par Playwright, la page affiche cinq articles au chargement, un seul après la saisie de « doctrine », et l'adresse devient `/articles?q=doctrine` sans rechargement du document. La pagination suit le même modèle :

```twig
<nav aria-label="Pagination">
    {% for number in 1..result.pages %}
        <a href="{{ path('articles', {q: query, page: number}) }}"
           hx-get="{{ path('articles', {q: query, page: number}) }}"
           hx-target="#results"
           hx-push-url="true"
           {% if number == result.page %}aria-current="page"{% endif %}>{{ number }}</a>
    {% endfor %}
</nav>
```

Chaque lien garde un vrai `href` : sans JavaScript, il navigue normalement. Avec HTMX, le même lien charge le fragment et met à jour l'historique. Ici, la pagination utilise `hx-push-url` : dans notre essai, le clic sur la page 2 a donné `/articles?q=&page=2`, et le retour arrière a ramené `/articles?q=`.

## Un formulaire validé côté serveur

Le formulaire est un [formulaire Symfony](https://symfony.com/doc/current/forms.html) ordinaire, avec son jeton CSRF, que HTMX envoie avec les autres champs. Seul le contrôleur change :

```php
#[Route('/contact', name: 'contact', methods: ['GET', 'POST'])]
public function __invoke(Request $request): Response
{
    $form = $this->createForm(ContactType::class);
    $form->handleRequest($request);
    $isHtmx = 'true' === $request->headers->get('HX-Request');

    if ($form->isSubmitted() && $form->isValid()) {
        if (!$isHtmx) {
            return $this->redirectToRoute('contact', [], Response::HTTP_SEE_OTHER);
        }

        return $this->render('contact/_sent.html.twig');
    }

    return $this->render($isHtmx ? 'contact/_form.html.twig' : 'contact/index.html.twig', ['form' => $form]);
}
```

Un formulaire valide renvoie un fragment de confirmation en HTMX, ou une redirection `303` hors HTMX. Un formulaire invalide renvoie le même fragment avec les erreurs. Le code `422` n'a pas besoin d'être écrit : `render()` le renvoie de lui-même quand on lui passe un formulaire soumis et invalide, ce que notre test confirme. Le gabarit du fragment est court :

```twig
<div id="contact-panel">
    {{ form_start(form, {attr: {'novalidate': 'novalidate', 'hx-post': path('contact'), 'hx-target': '#contact-panel', 'hx-swap': 'outerHTML'}}) }}
        {{ form_widget(form) }}
        <button type="submit">Envoyer</button>
    {{ form_end(form) }}
</div>
```

Trois pièges se rencontrent vite :

- **HTMX n'affiche pas les réponses 4xx par défaut.** Dans notre essai, la réponse `422` n'était pas insérée dans la page : HTMX la traite comme une erreur. Il faut l'autoriser, avec une balise de configuration dans le gabarit de base : `<meta name="htmx-config" content='{"responseHandling":[{"code":"204","swap":false},{"code":"[23]..","swap":true},{"code":"422","swap":true},{"code":"[45]..","swap":false,"error":true},{"code":"...","swap":true}]}'>`. Cette configuration reprend les règles par défaut de HTMX 2 en y ajoutant le `422`. Nous avons vérifié les deux cas dans le navigateur : avec la balise, le `422` est affiché, sans elle l'erreur reste invisible.
- **La validation native du navigateur passe avant HTMX.** Un champ `type="email"` rempli de façon invalide empêche l'envoi : la requête ne part jamais. L'attribut `novalidate` laisse le serveur valider, comme dans le gabarit ci-dessus.
- **Les identifiants peuvent entrer en collision.** Un formulaire nommé `contact` produit une racine `id="contact"`. Un conteneur du même nom donne deux éléments `#contact` après le remplacement : le nôtre s'appelle donc `contact-panel`.

## Accessibilité et référencement avec HTMX

Ces mises à jour partielles posent deux questions d'accessibilité : prévenir les lecteurs d'écran et préserver la navigation. Le conteneur de résultats porte `aria-live="polite"`, qui doit faire annoncer le changement de contenu (à vérifier avec un lecteur d'écran, ce que nous n'avons pas fait), et le fragment de confirmation du formulaire utilise `role="status"`. HTMX ne gère pas le focus à votre place : après un remplacement, vérifiez où il se trouve et déplacez-le si nécessaire. Notre article sur le [RGAA et l'expérience utilisateur](/article/normes-rgaa-les-cles-dune-experience-utilisateur-reussie-pour-tous), ainsi que la [remédiation technique RGAA sur Symfony](/article/rgaa-remediation-technique-symfony), détaillent les critères à contrôler.

Pour le référencement, le point fort de cette approche est sa dégradation élégante : chaque URL, appelée sans en-tête HTMX, renvoie une page HTML complète, puisque l'amélioration progressive part d'un site classique, et les liens `href` restent suivables comme sur n'importe quel site. Les combinaisons de paramètres de recherche créent en revanche des URL proches : prévoyez des balises canoniques si vous les exposez aux moteurs.

## HTMX, Symfony UX ou un framework JavaScript

Le choix dépend de la place que vous donnez au JavaScript.

- **HTMX** déclare chaque interaction dans le HTML. La lecture est directe, avec une logique entièrement côté serveur. Il suffit tant que l'état de l'interface tient dans des pages et des formulaires.
- **[Symfony UX](https://symfony.com/bundles/ux-turbo/current/index.html)** (Turbo, LiveComponent) vise le même objectif avec une intégration plus profonde à Symfony : Turbo pour la navigation, LiveComponent pour des composants Twig réactifs. Il tend à faire davantage de choses à votre place, ce qui accélère le démarrage mais masque une partie de la mécanique.
- **Un framework JavaScript** (React, Vue) devient pertinent pour les interfaces riches : éditeur, tableau de bord temps réel, usage hors connexion. Notre comparatif des [frameworks JavaScript](/article/quel-framework-javascript-choisir-node-js-react-js-vue-js-ou-angular) aide à trancher.

Pour un produit existant, HTMX présente un autre avantage : il s'ajoute page par page. Une application ancienne peut gagner en fluidité sans réécriture, ce qui relève d'une démarche de [modernisation progressive d'une application PHP legacy](/article/moderniser-application-php-legacy-sans-tout-reecrire). Pour un nouveau projet, notre article sur [les raisons de choisir Symfony](/article/pourquoi-choisir-symfony-pour-vos-projets) détaille les arguments en faveur du framework.

## Tester les fragments

Un fragment se teste comme une page, avec `WebTestCase`, en ajoutant l'en-tête HTMX :

```php
public function testFragmentWithHtmxHeader(): void
{
    $client = static::createClient();
    $client->request('GET', '/articles?q=symfony', server: ['HTTP_HX_REQUEST' => 'true']);

    self::assertResponseIsSuccessful();
    self::assertStringNotContainsString('<html', $client->getResponse()->getContent());
    self::assertSame('HX-Request, HX-Boosted, HX-History-Restore-Request', $client->getResponse()->headers->get('Vary'));
    self::assertSelectorTextContains('p', '1 résultat');
}
```

Le test du formulaire invalide vérifie le code et le contenu :

```php
public function testInvalidFormReturns422Fragment(): void
{
    $client = static::createClient();
    $crawler = $client->request('GET', '/contact');
    $form = $crawler->selectButton('Envoyer')->form(['contact[email]' => 'pas-un-email', 'contact[message]' => 'court']);
    $client->submit($form, [], ['HTTP_HX_REQUEST' => 'true']);

    self::assertResponseStatusCodeSame(422);
    self::assertStringNotContainsString('<html', $client->getResponse()->getContent());
    self::assertSelectorTextContains('#contact-panel', 'Cet e-mail est invalide.');
}
```

Notre suite de neuf tests, pour 23 assertions sous PHPUnit 13.4.3, couvre la page complète, le fragment, les requêtes portant `HX-Boosted` ou `HX-History-Restore-Request`, la pagination, l'absence de résultat, le formulaire invalide, le formulaire valide et la redirection hors HTMX. Ces tests s'exécutent sans navigateur, en moins d'une seconde. Réservez un outil de bout en bout comme Playwright aux comportements purement côté navigateur, comme l'historique ou l'affichage d'un `422`.

Avec HTMX, la logique d'interface reste côté serveur, là où votre équipe PHP sait déjà la traiter. Tant que les interactions restent des échanges de pages et de formulaires, c'est un bon compromis.
