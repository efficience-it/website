Relire du code écrit par un agent IA, c'est-à-dire en faire la revue de code, demande de changer la répartition du travail. Les contrôles mécaniques passent dans l'intégration continue (CI). Le relecteur humain se concentre sur ce qu'aucun outil ne vérifie : l'intention métier, les frontières d'architecture, la sécurité et les migrations de données. Cet article décrit une démarche concrète pour une équipe Symfony, du défaut typique à la checklist de relecture.

## Ce qui change quand personne n'a tapé le code

Trois effets rendent la relecture plus difficile qu'avant.

**Le volume augmente.** Un agent produit du code bien plus vite qu'un développeur ne le tape, et les pull requests peuvent s'accumuler plus vite que les relecteurs ne les traitent. Une équipe qui n'adapte pas sa démarche finit par valider sans lire.

**La qualité paraît meilleure qu'elle n'est.** Le code généré est souvent formaté, nommé proprement et commenté : la forme ne signale plus les approximations comme le faisait un code écrit à la hâte. Le défaut se cache derrière une apparence soignée.

**Les tests deviennent circulaires.** Quand le même agent écrit le code et les tests, ceux-ci passent presque mécaniquement, puisqu'ils décrivent ce que le code fait et non ce qu'il devrait faire. Ce problème s'inscrit dans une logique plus large, que développe notre article sur l'[échelle DALIA et la part d'IA dans le code](/article/echelle-dalia-niveaux-ia-developpement) : plus l'IA prend de place dans l'exécution, plus le jugement humain doit rester explicite.

## Les défauts typiques du code généré

Les cinq défauts les plus fréquents du code généré sont les API inventées, les dépendances superflues, la duplication et la sur-abstraction, les tests circulaires et les failles de sécurité. Ils passent facilement à travers une relecture rapide.

- **Des API inventées ou périmées** : une méthode de Doctrine ou de Symfony qui n'existe pas, ou qui a été retirée dans la version du projet. Le code est plausible, il ne s'exécute pas ou, pire, il s'exécute différemment.
- **Des dépendances ajoutées sans raison** : un paquet pour une fonction de trois lignes, ou un nom de paquet vraisemblable mais inexistant, qu'un attaquant peut ensuite enregistrer. On parle de slopsquatting.
- **De la duplication et de la sur-abstraction** : l'agent recrée un utilitaire qui existe déjà dans le projet, ou introduit une interface et trois classes pour un cas d'usage unique.
- **Des tests qui valident l'implémentation** : ils recalculent la valeur attendue avec la même formule que le code.
- **Des failles de sécurité** : entrées non validées, requêtes SQL construites par concaténation, secrets copiés dans le code ou dans un fichier de configuration.

Un exemple de test circulaire pour un calcul de remise, avec des montants en centimes et une remise en pourcentage :

```php
public function testTotalWithDiscount(): void
{
    $calculator = new PriceCalculator();

    self::assertSame(
        (int) round(10000 * (1 - 20 / 100)),
        $calculator->totalWithDiscount(10000, 20),
    );
}
```

Ce test répète la formule du code : si la formule est fausse, le test l'est aussi. Un test utile fixe le résultat attendu par le besoin et couvre les bornes hautes. Ici, `InvalidDiscount` est une exception du domaine :

```php
public function testTwentyPercentDiscount(): void
{
    self::assertSame(8000, (new PriceCalculator())->totalWithDiscount(10000, 20));
}

public function testFullDiscountGivesZero(): void
{
    self::assertSame(0, (new PriceCalculator())->totalWithDiscount(10000, 100));
}

public function testDiscountAboveOneHundredIsRejected(): void
{
    $this->expectException(InvalidDiscount::class);

    (new PriceCalculator())->totalWithDiscount(10000, 101);
}
```

Côté SQL, la version attendue passe toujours par des paramètres liés, jamais par une concaténation :

```php
$connection->executeQuery(
    'SELECT id, number, total FROM invoice WHERE customer_id = :customer',
    ['customer' => $customerId],
);
```

## Ce que la machine vérifie avant l'humain

Tout ce qui peut être contrôlé automatiquement doit l'être avant qu'un humain ouvre la pull request. C'est moins coûteux et surtout non négociable : une règle appliquée par la CI ne dépend pas de la fatigue du relecteur.

- **[PHPStan](https://phpstan.org/) au niveau maximal** repère les méthodes inexistantes, les types incohérents et les appels invalides, c'est-à-dire une partie des API inventées, à condition que les extensions Symfony et Doctrine soient installées et que la baseline reste mince. Nous détaillons les erreurs les plus fréquentes dans notre article sur [PHPStan niveau max sur Symfony](/article/phpstan-niveau-max-symfony-10-erreurs).
- **Rector en mode simulation** signale le code qui s'écarte des règles de modernisation du projet. Voir [Rector et l'évolution du code Symfony](/article/rector-et-ses-pouvoirs-maitrisez-levolution-de-votre-code-symfony).
- **Les tests** vérifient le comportement, à condition qu'un humain ait relu les cas attendus, comme le montre l'exemple de test circulaire ci-dessus.
- **Le mutation testing** mesure la capacité des tests à détecter un changement du code. [Infection](https://infection.github.io/) modifie le code (un `>` devient `>=`, une condition est inversée) et vérifie que les tests échouent. Un mutant qui survit signale un comportement que les tests ne vérifient pas, ou une assertion trop faible. Cela complète la relecture humaine des cas attendus sans la remplacer : un test qui reprend la formule du code peut très bien tuer ses mutants.
- **`composer audit`** compare les dépendances du fichier `composer.lock` aux avis de sécurité connus et fait échouer la commande s'il en trouve. Il ne protège pas contre un paquet inventé puis enregistré par un attaquant, qui n'a encore aucun avis publié : c'est le rôle de la ligne dédiée de la checklist.
- **Les hooks Git** exécutent les contrôles les plus rapides avant même le commit : voir notre comparatif [Lefthook, GrumPHP ou Husky](/article/git-hooks-php-lefthook-grumphp-husky).
- **Une CI bloquante** rend ces contrôles obligatoires. Pour que la CI soit réellement bloquante, déclarez le job `qualite` comme contrôle obligatoire dans la protection de branche (ou un ruleset) et exigez au moins une approbation humaine.

Un exemple de workflow GitHub Actions, à adapter à votre projet :

```yaml
name: Qualité
on: pull_request

permissions:
  contents: read

jobs:
  qualite:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: shivammathur/setup-php@v2
        with:
          php-version: "8.3"
          coverage: pcov
      - run: composer install --no-interaction --prefer-dist
      - run: composer audit --locked
      - run: vendor/bin/phpstan analyse --no-progress
      - run: vendor/bin/rector process --dry-run --no-progress-bar
      - run: vendor/bin/infection --threads=2 --min-msi=80 --git-diff-lines --git-diff-base=origin/${{ github.base_ref }}
```

Quelques précisions sur ce workflow. Le MSI (Mutation Score Indicator) est la part des mutants tués par les tests sur l'ensemble des mutants générés, ceux du code non couvert comptant comme survivants ; l'option `--min-covered-msi` le restreint au code couvert. Le seuil de 80 est un point de départ : mesurez d'abord le score actuel, puis relevez-le progressivement. Infection relance lui-même les tests, d'où l'absence d'étape PHPUnit séparée, et l'option `--git-diff-lines` limite l'analyse aux lignes modifiées pour garder une CI rapide, mais sur une petite pull request quelques mutants suffisent à faire varier fortement le score. Il lui faut un fichier de configuration `infection.json5` à la racine du projet, sinon il le demande de façon interactive. Alignez la version de PHP sur celle de la production, et épinglez les actions par empreinte (SHA) si votre chaîne d'approvisionnement l'exige.

## Ce que l'humain relit en priorité

Une fois les contrôles automatiques verts, le relecteur peut consacrer son attention à quatre zones.

### L'intention métier

Le code fait-il ce que la demande exigeait, y compris dans les cas limites ? C'est la question la plus difficile à automatiser. Lisez la description de la pull request avant le code : si elle ne permet pas de savoir ce qui était attendu, renvoyez-la à son auteur.

### Les frontières d'architecture

Un agent ne respecte pas toujours les couches du projet sans consigne explicite : il importe un composant du framework dans le domaine, ou court-circuite un service pour aller plus vite. Si votre projet suit une architecture hexagonale, vérifiez que [le domaine ne connaît toujours pas Symfony](/article/domain-ne-devrait-jamais-connaitre-symfony).

### La sécurité

Contrôlez les autorisations, pas seulement l'authentification : qui a le droit d'appeler cette route, de lire cet enregistrement ? Les [voters Symfony](https://symfony.com/doc/current/security/voters.html) formalisent ces règles et se relisent facilement, comme le détaille notre article sur les [stratégies de décision des voters](/article/voters-symfony-strategies-decision-performance). Vérifiez aussi les entrées utilisateur, les requêtes SQL et l'absence de secrets dans le diff. Si l'agent dispose lui-même d'accès à des outils, à des fichiers ou à un terminal, relisez ses permissions : l'[OWASP](https://genai.owasp.org/llm-top-10/) range l'octroi de fonctionnalités, de permissions ou d'autonomie excessives à un agent parmi les risques majeurs des applications fondées sur des LLM.

### Les migrations de données

Une migration de schéma ou de données est le changement le plus difficile à défaire. Relisez-la ligne à ligne : verrous de table, suppression de colonnes, volumétrie, possibilité de retour arrière.

## Les règles d'équipe qui rendent la démarche tenable

Cinq règles rendent la démarche tenable pour toute l'équipe : taille limitée des pull requests, auteur responsable, description du pourquoi, relecteur humain distinct et règles versionnées dans le dépôt.

- **Limiter la taille des pull requests.** Une pull request que l'on ne peut pas lire en une séance est découpée, même si l'agent l'a produite en une fois.
- **L'auteur humain reste responsable.** Celui qui ouvre la pull request doit pouvoir expliquer chaque ligne. « L'agent l'a écrit » n'est pas une réponse en relecture.
- **La description explique le pourquoi.** Elle indique l'intention, ce que l'agent a produit et ce qu'un humain a décidé ou modifié.
- **Un relecteur différent de l'auteur, jamais l'agent seul.** Un agent peut préparer une relecture, ce que fait, par exemple, le skill de relecture décrit dans nos [10 skills Claude Code pour une équipe Symfony](/article/skills-claude-code-equipe-symfony), mais il ne remplace pas l'approbation humaine.
- **Les règles du projet sont versionnées dans le dépôt.** Conventions, architecture, commandes de test et interdits doivent figurer dans un fichier lu par l'agent, comme nous l'expliquons dans notre retour sur [Claude comme assistant d'architecture](/article/claude-assistant-architecture-symfony-legacy).

Ces règles évitent aussi d'accumuler de la dette technique invisible : du code que personne ne comprend vraiment est un passif, même s'il passe les tests. Pour former l'équipe à ces outils, voyez [comment monter en compétence sur Claude Code](/article/monter-en-competence-claude-code).

Le programme de [SymfonyCon Varsovie 2026](https://live.symfony.com/2026-warsaw-con/schedule) comptait une conférence intitulée « Nobody typed this: reviewing agentic code ».

## Checklist de relecture

À copier dans le modèle de pull request de votre dépôt :

```markdown
- [ ] La description explique le pourquoi et distingue ce que l'agent a produit de ce qu'un humain a décidé.
- [ ] La pull request est assez petite pour être lue en une séance.
- [ ] La CI est verte : PHPStan, Rector, tests, mutation testing, `composer audit`.
- [ ] Chaque dépendance ajoutée existe, est maintenue et est réellement nécessaire.
- [ ] Les méthodes et API utilisées existent dans les versions du projet.
- [ ] Les tests vérifient le besoin et les cas limites, pas la formule du code.
- [ ] Aucune duplication d'un service ou d'un utilitaire existant.
- [ ] Les couches d'architecture sont respectées.
- [ ] Les autorisations sont vérifiées, les entrées validées, les requêtes paramétrées.
- [ ] Aucun secret dans le diff.
- [ ] Les migrations sont relues et réversibles, ou leur irréversibilité est assumée.
- [ ] L'auteur peut expliquer chaque partie du changement.
```
