Open source runs through the entire software industry. From application frameworks to databases, from orchestration tools to cryptographic libraries, nearly every production system relies on open source building blocks. Yet contributing remains a minority practice. For a developer, it is an unmatched lever for technical growth. For a company, it is a strategic investment whose returns far exceed the time invested. At Efficience IT, a [Symfony agency in France](/agence-symfony-france) (in French), we actively contribute to Symfony, API Platform, Twig, Sylius, Nelmio, and other projects in the PHP ecosystem.

## Why Contribute, and Where to Start

The first contribution is often the hardest. Not technically, but psychologically. Submitting code to recognized maintainers, exposing yourself to public review, accepting that a pull request may be rejected: all of this takes a kind of humility that corporate work does not always call for.

The most natural entry point remains a project you use every day. You already know its conventions, its limits, its pain points. An unclear error message, an outdated documentation page, a poorly handled edge case: these are all accessible contributions that bring real value. Read the project's CONTRIBUTING.md file, get familiar with the review process, and start with a focused change.

Once you take that first step, you will find that the contribution process is itself a learning experience. The rigor that mature projects demand, their quality standards, their attention to backward compatibility: all of this builds habits that transfer directly to your daily work.

## The Contribution Workflow in Practice

Contributing effectively means mastering a precise workflow. Fork the repository, create a dedicated branch for each change, and regularly sync your fork with the upstream repository. These basic mechanics quickly become automatic.

What sets a quality contribution apart is attention to context. Before writing a single line, take the time to understand the history of the feature involved. Check the related issues, previous PRs, and discussions in the project's communication channels. A change that looks obvious on the surface may have been deliberately rejected for backward compatibility or performance reasons.

Write explicit commit messages. Describe the problem solved, not the change made. Reference the corresponding issue. If your PR introduces a behavior change, document it and add the appropriate tests. Maintainers handle dozens of simultaneous contributions: the more self-contained and well-contextualized your PR is, the more likely it is to be merged quickly.

## The Code Review Culture

Code review in open source follows different dynamics than in an internal team. The reviewer knows neither your background nor your business context. They focus exclusively on the code, its consistency with the existing architecture, and its compliance with the project's standards.

Receiving feedback that asks for substantial changes is not a failure. It is how the process normally works. The Symfony maintainers, for example, set a high bar for backward compatibility, test coverage, and code clarity. Every exchange is a learning opportunity you will not find in any training course.

For a senior developer or lead, taking part in other contributors' code reviews is just as valuable as submitting your own PRs. It builds the ability to assess a change as a whole: performance impact, architectural consistency, long-term maintainability. These skills transfer directly to the technical leadership of a team.

## Maintaining an Open Source Project

Moving from contributor to maintainer changes your perspective radically. Maintaining a project means managing the flow of issues, prioritizing contributions, ensuring the quality of releases, and keeping a community alive.

Continuous integration becomes a central tool, as we show in our article on [running Postman tests with Newman in GitLab CI](/article/comment-executer-des-tests-postman-avec-newman-dans-gitlab-ci) (in French). A well-designed pipeline protects the project against regressions and frees maintainers from manual checks. Unit tests, integration tests, [static analysis with PHPStan](/article/comment-phpstan-peut-vous-aider-a-ameliorer-la-qualite-de-votre-code-php) (in French), coding standards checks, and a compatibility matrix across language and dependency versions: each layer reduces the reviewers' cognitive load and speeds up the contribution cycle.

Issue triage is an exercise in strategic prioritization. Not all requests are equal. An experienced maintainer can tell a critical bug from a marginal feature request, and a structural contribution from a cosmetic refactoring. This discernment is a core skill of a technical lead.

## Open Source as a Strategic Investment

For a company, contributing to open source is not philanthropy. It is a rational calculation with multiple, measurable benefits.

The first return is direct: influencing the roadmap of the tools your stack relies on. By contributing regularly to a framework, you understand its evolution before it is released, you can steer technical decisions in a direction that fits your needs, and you anticipate breaking changes. This active technology watch is worth far more than a passive one.

The second return concerns hiring and retention. Talented developers look for environments where they can grow. An open source contribution policy, with dedicated time and structured coaching, is a strong signal that attracts the most demanding profiles. It is one of the [reasons to join Efficience IT](/article/7-bonnes-raisons-de-rejoindre-efficience-it) (in French) that our developers highlight. A weekly half-day of contribution is a small effort compared to the consequences of a failed hire or high turnover.

### Inner Source: Applying Open Source Practices Internally

The inner source model brings open source practices inside an organization. Internal repositories are open to all of the company's developers. Contributions go through pull requests reviewed by the owning teams. Documentation is public internally.

This model breaks down organizational silos. It lets one team fix a bug in a library maintained by another team, without going through a support ticket and a queue. It promotes the spread of best practices and the emergence of common standards. For an organization larger than a single team, inner source is a considerable velocity booster.

### Licenses and Governance

Choosing a license is not an administrative formality. Just like following the [PSRs in PHP](/article/qu-est-ce-que-les-psrs-et-a-quoi-servent-ils) (in French), it determines how your code can be used, modified, and redistributed. MIT, Apache 2.0, GPL, AGPL: each license carries a different view of intellectual property and reciprocity.

For a company that publishes code, the question of governance arises quickly. Who decides the roadmap? How are external contributors handled? What level of support is expected? These questions deserve answers from the start, before the project grows. A clear GOVERNANCE.md file, a strict semantic versioning policy, and a documented release process are the foundations of a lasting project.

### Sustaining Open Source Over the Long Term

The open source ecosystem suffers from a structural imbalance: millions of companies depend on projects maintained by a handful of developers, often volunteers. Incidents involving under-maintained critical dependencies regularly remind us how fragile this model is.

Sustaining open source takes a collective commitment. Foundations play a structuring role by funding maintainers and providing governance for critical projects. In the PHP ecosystem, [the PHP Foundation celebrated its third anniversary](/article/la-fondation-php-souffle-ses-trois-bougies) (in French) as it became a pillar of this collective governance. Sponsorship programs on GitHub or Open Collective allow direct support. But the most valuable contribution remains time: skilled developers who regularly spend hours on code review, issue triage, and maintenance of the projects they depend on.

For an architect or a CTO, the question is not whether to contribute to open source, but how to structure that contribution so that it is sustainable and aligned with the organization's technical strategy.
